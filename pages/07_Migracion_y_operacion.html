Ambientes y promoción

Diseño propuesto: desarrollo aislado en un ambiente Automotive con capacidades equivalentes, integración y ensayo con datos sintéticos o una muestra autorizada, UAT con personas representativas y producción como destino de una liberación aprobada. No se ha comprobado ni creado esa topología. La conectividad Microsoft se prueba con un tenant y buzones autorizados antes de acceder al servicio productivo.

El repositorio versiona metadata y configuración FFT con un manifiesto explícito. Cada paquete incluye objetos y campos dependientes, permisos mínimos, clases, flows, LWC, páginas, reportes y configuración por ambiente. Los secretos se suministran mediante el mecanismo de credenciales aprobado, nunca en Apex, JavaScript o documentos.

El pipeline propuesto valida el manifiesto, referencias, API version, compilación, pruebas Apex significativas, seguridad y despliegue de validación en el ambiente autorizado. Después ejecuta pruebas de contratos e interfaces y genera evidencia asociada a versión. La promoción a producción necesita la aprobación de liberación; este paquete no ejecutó ningún pipeline.

Orden de metadata y configuración

1. Confirmar licencias, features y referencias estándar disponibles. 2. Preparar maestros y extensiones de esquema sin activar procesos. 3. Desplegar servicios, validaciones, flows y permisos mínimos. 4. Incorporar LWC, navegación, Experience, plantillas y reportes. 5. Configurar endpoints, catálogos y asignaciones por ambiente. 6. Cargar datos según dependencias. 7. Validar acceso y activar procesos en el orden aprobado.

No se cambia un MasterDetail histórico a Visit por sustitución textual del XML. Los nuevos lookups propuestos FFT_Visit__c se crean con su contrato de obligatoriedad y control de acceso; se revisan rollups, cascadas, propiedad y automatizaciones que dependían de ControlledByParent. El mapping identifica los dos vínculos distintos de Temas a la consultoría y evita colapsarlos.

Las automatizaciones compartidas se revisan por impacto. Las 82 Flow candidatas incluyen dependencias compartidas; sólo se despliega o modifica el subconjunto aprobado. Una referencia estática sin invocación probada no demuestra que un componente se pueda retirar.

Carga, idempotencia y reconciliación

Cada ejecución registra runId, versión de mapping, filtro de extracción, marca temporal, archivo o lote, checksum, conteos y estado. El crosswalk usa SourceOrgId + SourceObjectApi + SourceId18 como identidad técnica y conserva TargetId, clave funcional y resultado. Una clave natural ambigua se envía a excepción; no se resuelve por la primera coincidencia.

Los maestros compartidos se emparejan con claves corporativas aprobadas y no se duplican por utilizar una clave legacy. Para registros migrados exclusivos se propone FFT_LegacyKey__c como External ID y unique donde el objeto lo permita; si no lo permite, un registro controlado de correspondencias conserva la unicidad. Las fórmulas y rollups no se insertan como valores: se recalculan y se concilian contra la regla aprobada.

Por objeto y lote debe cumplirse: extraídos = aceptados + rechazados justificados + excluidos aprobados, con categorías excluyentes. Para cada aceptado debe existir una correspondencia única y referencias válidas. Los importes se comparan por moneda y precisión, y los indicadores por periodo, dealer, versión y estado. Se compara la relación padre-hijo, no sólo el conteo de filas.

El delta usa marca de modificación y solapamiento controlado para no perder escrituras en el límite, con deduplicación por clave y versión. Las bajas se extraen mediante el mecanismo autorizado disponible y se procesan según retención. Repetir un lote no crea duplicados; un timeout obliga a consultar el resultado antes de repetir una operación no idempotente.

Archivos e historial

Files se carga después de resolver IDs de negocio. El manifiesto conserva documento, versión, nombre, tamaño, tipo y hash, y aplica ContentDocumentLink sólo al destino autorizado. No se usan URLs o IDs del origen como identificadores reutilizables. Las políticas de versiones históricas y autoría requieren aprobación; cualquier campo de auditoría no soportado se conserva en un registro de trazabilidad separado.

El acceso a un documento se prueba desde el registro, por enlace directo, por API y desde el canal dealer. Migrar un archivo no implica hacerlo público. Si no se resuelve la persona o el ámbito, el registro se conserva en excepción sin un enlace público de conveniencia.

Operación y recuperación

Cada interfaz registra correlación, dominio, operación, clave lógica, versión, actor técnico, resultado, duración y número de intento. Los errores recuperables utilizan reintentos acotados con espera incremental; errores de autorización, contrato o dato pasan a una cola de atención. Ningún log incluye tokens ni contenidos sensibles completos.

Los responsables operativos monitorizan colas, jobs detenidos, errores de sincronización, fallos de PDF y diferencias de conciliación. Un tablero de operación debe mostrar antigüedad del pendiente, último éxito, responsable y vínculo a evidencia. La retención y los umbrales se aprueban con Nissan; no se infieren del sandbox.

Antes de aceptar escrituras en destino se puede revertir la activación manteniendo el origen como autoridad. Después se requiere capturar y conciliar todas las escrituras aceptadas en destino antes de recuperar o devolver tráfico. Una reversión de metadata no recupera datos. El RTO y la ventana de recuperación quedan pendientes; el objetivo propuesto de corte es cero escrituras aceptadas perdidas.
